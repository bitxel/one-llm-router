# Research: Full OpenAI API Gateway

**Feature**: 006-openai-api-gateway
**Spec**: `specs/006-openai-api-gateway/spec.md`
**Created**: 2026-04-26
**Status**: Resolved baseline

This research pass identifies the API surface and risk boundaries for turning one-llm-router into a complete OpenAI Platform-compatible gateway. Sources are official OpenAI documentation checked on 2026-04-26, existing project specs, local codex-lb source, and official comparable gateway documentation.

## Source Findings

- The OpenAI API reference describes RESTful, streaming, and realtime APIs, and documents Bearer API-key authentication. It also documents `X-Client-Request-Id` for client-side correlation and notes OpenAI's `v1` backwards-compatibility stance.
- The current API reference inventory includes Responses and Conversations; Webhooks; Platform APIs for Audio, Videos, Images, Embeddings, Evals, Fine-tuning, Batches, Files, Uploads, Models, and Moderations; Vector Stores; ChatKit; Containers; Skills; Realtime; Administration; Chat Completions; and Legacy APIs.
- Realtime WebSocket docs describe a server-to-server WebSocket connection at `wss://api.openai.com/v1/realtime?model=...` with an API-key Authorization header, while recommending WebRTC for browser/mobile clients.
- Realtime WebRTC docs describe browser/mobile-oriented WebRTC access through either ephemeral API keys generated by the OpenAI REST API or a unified interface where the developer-controlled server authenticates to OpenAI with a standard API key.
- Realtime SIP is documented as a separate call-control/media integration surface, not as ordinary `/v1/*` HTTP forwarding.
- Uploads are not ordinary JSON calls: upload parts are byte chunks, each part can be up to 64 MB, the upload can reach 8 GB, and parts can be added in parallel before completion.
- Existing one-llm-router specs define API-key accounts as OpenAI Platform-compatible for `/v1/*`, while OAuth ChatGPT accounts use explicit ChatGPT Codex backend mappings rather than arbitrary Platform forwarding. Feature 006 expands those OAuth mappings to include `/v1/chat/completions`, `WS /v1/responses`, OAuth `GET /v1/models` facade, and selected Codex-native `/backend-api/*` paths. Router-local usage observability is an Admin API concern and is exposed through `GET /api/admin/usage`; codex-lb-shaped `GET /api/codex/usage` and `GET /api/codex/usage/` are not adopted as data-plane routes. `/v1/audio/transcriptions` is explicitly deferred from 006.

## Decision 1: Treat full gateway as core data-plane behavior, not a plugin

- **Decision**: Model this as Feature 006 core data-plane expansion.
- **Rationale**:
  - The feature changes the `/v1/*` and selected `/backend-api/*` provider-compatible contract and account eligibility behavior.
  - Plugins in this codebase express user-toggleable capabilities, not URL ownership.
  - The setup gate, request logging, account selector, provider forwarder, and native data-plane errors are core infrastructure.
- **Alternative**: Add a plugin that owns the OpenAI API surface.
  - **Rejected**: Project rules forbid plugins from binding URL paths.

## Decision 2: Full Platform gateway is API-key only, with explicit OAuth Codex mappings

- **Decision**: P0 OpenAI Platform gateway behavior applies to API-key upstream accounts according to the coverage matrix. ChatGPT OAuth accounts are eligible for explicit Codex-backed compatibility mappings: `/v1/responses`, `WS /v1/responses`, `/v1/responses/compact`, `/v1/chat/completions`, `GET /v1/models`, `/backend-api/codex/responses`, `WS /backend-api/codex/responses`, `/backend-api/codex/responses/compact`, `/backend-api/codex/models`, and `/backend-api/transcribe`. `/api/codex/usage`, `/api/codex/usage/`, and `/v1/audio/transcriptions` are not supported data-plane routes in 006.
- **Rationale**:
  - OpenAI Platform APIs use API-key Bearer authentication.
  - Project Feature 003 states ChatGPT OAuth tokens map to ChatGPT Codex backend, not arbitrary Platform `/v1/*`.
  - codex-lb demonstrates a workable OAuth Chat Completions pattern by converting Chat Completions requests into Responses payloads, calling the ChatGPT Codex `/codex/responses` upstream with the OAuth access token, and converting Responses SSE events back into Chat Completions chunks or objects.
  - codex-lb demonstrates transcription compatibility by exposing `/backend-api/transcribe` and `/v1/audio/transcriptions`, then forwarding multipart audio to the ChatGPT Codex `/transcribe` upstream with the OAuth access token and optional `chatgpt-account-id`; 006 adopts only the Codex-native `/backend-api/transcribe` path.
  - codex-lb demonstrates additional compatibility surfaces for `WS /v1/responses`, `GET /v1/models`, `GET /api/codex/usage`, and `GET /api/codex/usage/`; 006 adopts `WS /v1/responses` and OAuth `GET /v1/models`, but keeps usage observability under the router-owned Admin API and keeps `/v1/audio/transcriptions` deferred by user decision.
  - Routing all endpoints through OAuth would fabricate compatibility and cause confusing provider failures.
- **Alternative**: Try OAuth for every `/v1/*` path.
  - **Rejected**: Existing research already documents this as unsafe and unsupported.
- **Alternative**: Forward OAuth Chat Completions directly to an OpenAI Platform `/v1/chat/completions` upstream.
  - **Rejected**: ChatGPT OAuth tokens are Codex backend credentials, not Platform API keys.

## Decision 3: Transport shape drives the implementation and test matrix

- **Decision**: Classify endpoint groups by transport shape before implementation: JSON, multipart, binary download, SSE, WebSocket, and long-running resource lifecycle.
- **Rationale**:
  - The hard part is not path enumeration alone; it is preserving wire behavior without unsafe buffering or logging.
  - Current `/v1/responses` tests cover only a narrow JSON/SSE subset.
  - Files, uploads, audio, images, videos, and batch resources require binary/multipart behavior.
- **Test impact**:
  - Local mock-upstream tests must cover each transport shape.
  - Live smoke should be small and low-cost, not a full conformance suite.

## Decision 4: Administration API is excluded from 006

- **Decision**: Do not proxy OpenAI Administration API endpoints in 006.
- **Rationale**:
  - These endpoints can mutate organizations, projects, users, groups, roles, service accounts, API keys, certificates, and rate limits.
  - They may require admin API-key credentials rather than normal project API keys.
  - OpenAI's official OpenAPI endpoint inventory checked on 2026-04-27 lists usage and cost endpoints as organization administration routes such as `/v1/organization/usage/*` and `/v1/organization/costs`.
  - one-llm-router does not yet have admin RBAC strong enough to safely expose these actions through a general data-plane gateway.
  - The user explicitly decided on 2026-04-26 that OpenAI Administration API is not included in 006.
- **Future work if reconsidered**:
  - Separate credential type.
  - Explicit audit events.
  - Stronger operator permission model.
  - Separate live tests using restricted admin test organization.

## Decision 5: OpenAI Realtime is deferred from initial 006

- **Decision**: Do not support OpenAI Realtime server-to-server WebSocket in initial 006. Do not proxy WebRTC or SIP in 006.
- **Rationale**:
  - WebSocket is a gateway-friendly bidirectional transport.
  - OpenAI documents WebSocket server-to-server auth with standard API keys.
  - The user decided on 2026-04-26 that OpenAI Realtime WebSocket should be deferred with other expanded Platform API groups.
  - WebRTC and SIP rely on browser/mobile media setup, ephemeral key minting, signalling, or call-control semantics that are not the same problem as forwarding HTTP and WebSocket data-plane traffic.
  - ChatGPT OAuth tokens in this project are Codex backend credentials, not OpenAI Platform API credentials, so using them for Realtime would fabricate support.
- **Future work if reconsidered**:
  - A future feature can decide whether the router should mint Realtime client secrets for browser/mobile clients or proxy SIP call-control endpoints.

## Decision 6: Prioritize current/common APIs before beta, newer, and legacy groups

- **Decision**: Initial 006 P0 covers API-key Platform-compatible Responses, Conversations, Chat Completions, and Models, plus explicit OAuth/Codex compatibility paths. Embeddings, Moderations, Images, Audio, Videos, Files, Uploads, Vector Stores, Batches, Fine-tuning, Evals, and OpenAI Realtime WebSocket are deferred.
- **Rationale**:
  - The initial README-facing support matrix must match what the router is expected to support first, not the broader eventual gateway ambition.
  - The deferred groups need multipart, binary/media, resource lifecycle, or bidirectional transport tests before they are promoted.
  - Legacy Assistants, legacy Completions, and Realtime Beta remain compatibility work, not the baseline definition of the initial 006 gateway slice.

## Decision 7: Selected Codex-native `/backend-api/*` paths are in scope

- **Decision**: Support only `/backend-api/codex/responses`, `WS /backend-api/codex/responses`, `/backend-api/codex/responses/compact`, `/backend-api/codex/models`, and `/backend-api/transcribe` as client-facing Codex-native data-plane compatibility paths.
- **Rationale**:
  - Codex-native clients and codex-lb-compatible integrations use these paths directly.
  - They are data-plane compatibility paths, not router-owned admin APIs, so they must stay outside the admin envelope.
  - Usage/status observability is not a Codex transport operation in this router; it is a router-owned Admin API read.
  - Arbitrary ChatGPT `/backend-api/*` proxying would expand the trust boundary too far and could expose undocumented product/backend surfaces without account, logging, or permission semantics.
- **Alternative**: Expose all `/backend-api/*` paths as a transparent proxy.
  - **Rejected**: This would violate the fail-fast and no-fabricated-compatibility rules. 006 should support only routes with explicit semantics and tests.

## Decision 8: WebSocket relay dependency

- **Decision**: Use `github.com/coder/websocket` pinned to `v1.8.14` for the downstream WebSocket accept path and the upstream Codex WebSocket dial path.
- **Rationale**:
  - Go's standard library does not implement the WebSocket protocol.
  - The package supports server-side accepts and client-side dials in one dependency.
  - The package is context-aware and keeps RFC 6455 frame parsing, masking, ping/pong, and close handling out of router-owned code.
  - The dependency is small enough for the project's direct-dependency boundary and was approved by the user on 2026-04-26.
- **Alternatives Considered**:

| Alternative | Pros | Cons | Why Rejected |
|---|---|---|---|
| `gorilla/websocket` | Widely used | Older API and more manual lifecycle/backpressure handling | Less aligned with the context-first relay plan |
| `nhooyr.io/websocket` | Context-first API | Predecessor package; less preferred than the Coder-maintained import path | Use the maintained Coder package directly |
| Hand-rolled RFC 6455 | No dependency | High correctness and security risk | Violates the plan's no-hand-rolled-protocol rule |

### codex-lb Support Detail

- codex-lb is explicitly a ChatGPT account load balancer with usage tracking, dashboard, API keys, and OpenAI-compatible clients.
- Its route inventory is narrow and Codex-oriented: `/backend-api/codex/responses`, `WS /backend-api/codex/responses`, `/backend-api/codex/responses/compact`, `/backend-api/codex/models`, `/backend-api/transcribe`, plus `/v1/responses`, `WS /v1/responses`, `/v1/responses/compact`, `/v1/chat/completions`, `/v1/audio/transcriptions`, `/v1/models`, `/api/codex/usage`, and `/api/codex/usage/`.
- Chat Completions is implemented as a compatibility adapter into the Responses/Codex stream, not as transparent forwarding to OpenAI Platform Chat Completions.
- The request adapter accepts OpenAI Chat Completions fields, validates unsupported shapes, normalizes `messages` into Responses `instructions` plus `input`, maps function tools and `web_search_preview`, maps `response_format` to Responses `text.format`, maps `reasoning_effort` to `reasoning.effort`, rejects unsupported stored/multi-choice intent such as `store=true` and `n>1`, maps token limits to `max_output_tokens`, and forces the upstream payload into `ResponsesRequest` with explicit `store:false`.
- The route always sets `responses_payload.stream = True`, calls the normal OAuth-backed Responses stream path, and then either emits Chat Completions SSE chunks for streaming clients or collects the Responses stream into a non-streaming `chat.completion` object.
- Real Codex backend traffic may return Responses SSE with a JSON `Content-Type`; the adapter treats `data:`, `event:`, and SSE comment-prefixed bodies as Responses SSE so downstream Chat Completions streaming remains `text/event-stream` instead of failing on the header mismatch.
- The upstream call decrypts the selected account's OAuth access token, adds `Authorization: Bearer <access_token>` and `chatgpt-account-id` when available, and posts the converted Responses payload to `<upstream_base>/codex/responses`.
- `/backend-api/transcribe` and `/v1/audio/transcriptions` share the transcription request path in codex-lb; `/v1/audio/transcriptions` requires model `gpt-4o-transcribe` there, but 006 intentionally adopts only `/backend-api/transcribe`.
- The transcription upstream target is `<upstream_base>/transcribe`; the upstream call adds `Authorization: Bearer <access_token>` and optional `chatgpt-account-id`, then forwards the multipart `file` and optional `prompt`.
- WebSocket support is Codex Responses WebSocket. The upstream connection builds `Authorization: Bearer <access_token>`, adds `chatgpt-account-id` when available, ensures `OpenAI-Beta: responses_websockets=2026-02-06`, and maps the upstream URL to `/codex/responses`.
- The local integration tests are deeper around compatibility behavior than endpoint breadth: Responses, Chat Completions translation, transcription, SDK compatibility, WebSocket turn-state/reconnect/failure modes, tool normalization, and explicit rejection of unsupported OpenAI Platform features such as some built-in tools, file IDs, audio input, `store=true`, and incompatible truncation/conversation combinations.
- No local evidence was found for codex-lb support of Platform Embeddings, Images, Files, Uploads, Vector Stores, Batches, Fine-tuning, Evals, OpenAI Webhooks, OpenAI Administration API, or OpenAI Realtime `/v1/realtime`.

### Implications for 006

- Keep codex-lb as a compatibility-test reference for Codex/OAuth accounts, especially for `/v1/chat/completions`, `WS /v1/responses`, and `GET /v1/models`, but not as the coverage baseline for a complete OpenAI Platform gateway. Its usage paths are reference-only and not part of 006 data-plane scope.
- Keep full OpenAI Platform gateway support API-key-only, while adding explicit OAuth compatibility mappings where the ChatGPT Codex backend can honestly support them. Comparable broad gateways use provider/API-key or platform-token models; they do not treat ChatGPT OAuth tokens as general OpenAI Platform credentials.
- Implement OAuth Chat Completions as an adapter over the existing OAuth Responses transport: Chat Completions request validation/normalization -> Responses upstream stream -> Chat Completions stream/object reconstruction.
- Do not include Embeddings, Moderations, Images, Audio, Videos, Files, Uploads, Vector Stores, Batches, Fine-tuning, Evals, or OpenAI Realtime WebSocket in the initial 006 support matrix. Keep `/backend-api/transcribe` as a selected Codex-native compatibility path, and keep `/v1/audio/transcriptions` unsupported.
- Add selected `/backend-api/*` support and OAuth `GET /v1/models` facade as explicit allowlist entries for Codex-native clients, not as arbitrary ChatGPT backend or `/api/*` proxying.
- Add router-local usage observability as `GET /api/admin/usage` with Admin envelope/OpenAPI contract instead of codex-lb-shaped data-plane aliases.
- Defer OpenAI Realtime server-to-server WebSocket. Portkey and New API both expose OpenAI Realtime as a WebSocket-style gateway surface, but this project keeps it out of initial 006; codex-lb's Responses WebSocket is a different Codex transport and is now covered on `WS /v1/responses` and `WS /backend-api/codex/responses`.
- Split future implementation and tests by endpoint transport shape, not only by path count. Portkey/New API show broad endpoint matrices; codex-lb shows that compatibility adapters need explicit negative tests where the upstream transport cannot honestly support an OpenAI feature.
- Continue excluding OpenAI Administration API from 006. None of the checked comparable gateway docs provide a clear pattern for safely proxying OpenAI organization/project administration through a general data-plane gateway.
